# Agent Note: 官方 Harness 变更自动进入桌面发布通道

Status: implemented

[English](2026-09-01-automatic-desktop-upstream-release.md) | 中文

## Problem

桌面应用可以从 GitHub 通道安装发布版本，但发布该通道仍需要维护者发现 DeepSeek Harness 官方提交、更新固定版本与桌面版本，再启动发布工作流。应用更新器不能直接消费官方源码仓库，因为源码提交不是带有 electron-updater 元数据、经过签名和测试的 Windows 安装器。

## Decision

一个定时 GitHub 工作流每五分钟检查配置的官方分支头与桌面包版本。分支头变化时，它会推进 `.github/desktop-upstream.json`，使桌面发布版本的主版本号、次版本号与补丁号和官方桌面包保持一致，再把两项变更推送到 `main`，然后显式派发现有的「Desktop Release」工作流。这三个版本号不变时，后续官方提交会单调递增桌面 `rc` 编号。流程不依赖 `GITHUB_TOKEN` 产生的 push 去触发另一个工作流。

同步流程还会查询与当前桌面版本匹配的发布。如果该发布因构建失败、中断或派发失败而缺失，后续运行会再次派发同一版本，而不是继续递增。这样，仓库记录期望的官方版本，GitHub Releases 则记录经过测试的桌面产物是否真实存在。

「Desktop Release」仍是发布权威。它检出记录的官方提交，只应用桌面适配，运行桌面测试与官方构建，封装安装器，启动已封装的 Harness Web 运行时，并且只在所有检查通过后发布安装器、blockmap 与 `latest.yml`。因此，破坏兼容性的上游变更会让通道停留在最后一个可用发布，而不会交付损坏更新。

## Alternatives considered

**让已安装应用直接下载官方仓库文件。** 源码文件无法安全替换 Electron 应用资源，缺少安装器元数据，也没有通过桌面适配构建。

**不经过构建门禁就发布每个检测到的官方提交。** 这只能自动化发现，同时移除了保证更新安全的证据。

**要求维护者在每次官方变更后推送发布标签。** 这保留了现有人工间隔，无法满足无人值守更新。

## Consequences

当官方分支与桌面适配保持兼容时，新的已测试桌面发布会在无需用户或维护者操作的情况下出现，应用通过现有启动检查或手动检查发现它。破坏兼容性的官方变更会显示为失败的 GitHub 工作流，并在同一个桌面版本上持续重试，直到适配得到修复；已安装应用会继续提供最后一个成功发布。
